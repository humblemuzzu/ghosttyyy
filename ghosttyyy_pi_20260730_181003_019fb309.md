## why `apply_patch` is better

### one tool handles everything

one envelope can:

- create files
- update files
- delete files
- move files
- modify several files together

today the model must choose between `edit`, `write`, and sometimes `bash`. that extra choice creates mistakes.

### related changes are validated together

with `edit`, a three-file refactor needs three calls. call one and two can succeed before call three fails, leaving a half-finished refactor.

`apply_patch` first calculates every change in memory. if one hunk is stale or incorrect, it writes nothing.

### stronger safety

the local port includes:

- symlink and hard-link refusal
- canonical-path and case-alias checks
- sorted multi-file locks
- permission checks over every touched path
- rollback after ordinary write failures
- placeholder rejection such as `// ... rest unchanged`
- protection against `Add File` accidentally overwriting an existing file

your mac-specific `realpathSync.native` fix is especially worthwhile. it prevents the case-alias deadlock found during real testing.

### smaller, clearer tool surface

the model learns one diff-like language instead of separate creation and replacement schemas. openai models additionally get grammar-constrained generation. your tests show opus, codex, kimi, and deepseek-pro can use it, although weaker models remain unreliable.

## why i would not cut over today

these are concrete blockers:

1. **native `edit` and `write` would return.**  
   deleting your custom registrations does not remove pi’s built-ins. upstream explicitly filters them during `session_start`. the local port does not currently do that.

2. **moves overwrite existing destinations.**  
   `apply-patch.ts:680-687` replaces the destination without requiring an explicit delete first.

3. **ambiguous hunks choose the first match.**  
   `lib/codex-patch.ts:240-260` does not retain your old `edit` tool’s uniqueness protection. a short repeated block can modify the wrong occurrence.

4. **anchored addition-only hunks append at the file end.**  
   `lib/codex-patch.ts:294-299` ignores the located `@@` anchor for pure insertions.

5. **tracking is not transactional.**  
   local `saveChanges()` simply calls `saveChange()` repeatedly. if record two fails, record one remains even though the filesystem is rolled back. upstream has cleanup and temporary-record writes.

6. **undo remains one file at a time.**  
   a move is tracked as source deletion plus destination creation. undoing only one side temporarily leaves an inconsistent state.

7. **exact file creation has gaps.**  
   the format cannot currently create an empty file or preserve “no final newline”.

8. **cutover wiring is still pending.**  
   `Task`, aliases, system prompt, subagent rendering, docs, and verification inventories still mention `edit`/`write`.

## my verdict

**use `apply_patch` as the eventual replacement.** its multi-file validation, rollback, path protection, and unified interface are better than the current separate tools.

but first fix the blockers above and add real commit-failure/tracker-failure tests. then:

1. hide native `edit` and `write`
2. retarget aliases and `Task`
3. update the prompt
4. delete only `edit-file.ts` and `create-file.ts`
5. keep everything else
6. rerun the cross-provider matrix

so the answer is: **`apply_patch` wins architecturally, but the current local port needs one hardening pass before permanent cutover.**
